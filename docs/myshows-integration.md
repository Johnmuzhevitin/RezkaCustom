# MyShows integration

Version 0.6.0 adds opt-in automatic episode synchronization. The native MyShows history confirmation flow was verified before implementation; see [the feasibility test](myshows-verification-2026-11-01.md). This integration does not mark whole Rezka titles or change the existing `/continue/` actions.

## Movies (0.7.0)

Films share the existing thresholds, played-coverage/confirmed-position calculation, manual completion, account isolation, queue, cancellation and recovery. The panel changes to **Текущий фильм**, **Засчитать фильм** and **Фильм в MyShows** on movie pages; settings and journal search cover both media types. Existing episode records and keys remain unchanged. The serialized `episode` container also holds movie metadata with `kind: "movie"`; movies have `movie:<rezkaId>` keys and a separate `movieId`, never synthetic season/episode numbers.

Movie detection requires the native `initCDNMoviesEvents` initializer for the current Rezka title and no episode/season controls or conflicting series initializer. This includes standalone animation and cartoons; an unselected series is never inferred to be a film. The request uses the official [`movie` payload](https://myshowsme.github.io/myshows-scrobbler-api/ru/scrobbling/request), with IMDb, title and optional year. Automatic native approval requires `action=scrobble`, `match=exact`, `objectType=movie` and a positive numeric object ID, following the existing observed response contract. A different or incomplete response requires reconciliation, never a guessed match or duplicate POST.

The source-scoped history card must link to exactly one movie ID matching the accepted API result. Pending records require explicit exact-match evidence and the configured progress before **Подтвердить** is clicked. Approved records are checked on `/movie/<id>/`: only the selected **Посмотрел** option in `.MovieDetails .StatusBar__option` establishes success. **Буду**, **Не смотрел**, episode checkboxes and missing/ambiguous controls never establish a completed movie mark. Later manual changes on MyShows are not imported.

Read-only inspection in the user's existing Chrome on 2026-11-02 confirmed the Rezka movie initializer, absent episode controls, top-document video and IMDb link, plus both watched and unwatched native MyShows movie statuses. No movie scrobble was submitted during that initial inspection.

### Native movie history repair (0.7.1)

A movie history card exposed an incorrect 0.7.0 fixture assumption: the movie link lives in a poster wrapper beside `.ScrobbleCard__info`, inside `.ScrobbleCard__row`. Searching only inside the info block incorrectly produced `match` even when MyShows had mapped the film correctly. The adapter now inspects links in that same row, requiring exactly one info block and one unique same-origin movie ID. It still rejects conflicting episode links, mismatched IDs and duplicate sources; it never searches neighbouring rows for a usable match.

`tests/fixtures/myshows-movie-history.html` preserves the observed nesting with synthetic record data. The original adapter failed the fixture with `match`; the corrected adapter passes. Worker/adapter checks cover retrying an already-submitted manual record while automatic marks are paused without another POST, and retaining the manual-confirmation requirement if exact API evidence is absent.

The corrected source was also executed in a temporary isolated developer context on the real MyShows history page. With approval disabled it resolved the pending movie and returned `manual`, rather than the erroneous `match`. The user's existing submission was confirmed through its native button; the adapter then returned the approved movie ID, and on the film page it returned `watched: true` from the selected **Посмотрел** status. No new scrobble was submitted and no credentials were read. This verifies the site adapter and remote recovery, not the updated installed worker/panel; those still require an extension reload and **Проверить** on the existing journal entry. See [verification history](verification-history.md) for the packaged build and browser boundary.

## Panel during playback (0.6.5)

The current episode appears above a collapsed **Настройки MyShows** disclosure. Its credited percentage and threshold remain available regardless of the selected journal filter. Retry, cancel, resume, result and external episode link are presented in the current context. Completed episodes have an explicit result instead of a disabled completion button. Queue, attention and history counts are attached to their filters.

Every history row (completed, cancelled or reset) shows a title, episode/movie label and compact icons. Journal actions use icons with Russian accessible labels and tooltips. A circled green check indicates a verified completed mark; its tooltip and accessible name state the status. Status text, date, manual origin, cancellation warnings, reset guidance and events are available in a shared nonmodal information popover. Long titles truncate in the row but remain complete in tooltips and information. Active progress and attention errors remain visible in their journal rows.

The trash icon deletes a cancelled, unsent record locally, including while disconnected. The worker checks the current account and persisted status again: successful marks, reset records, active work and uncertain submitted requests cannot be deleted. Deletion removes the entry and its detailed history; only its account/media key remains in `state.removed` to prevent late player batches or browser restarts from silently recreating the cancelled request. No MyShows request is sent. The current-view block explains that automatic marking remains stopped and offers **Возобновить учёт** for a fresh viewing or an explicit manual mark. Either action clears that key and creates a new record with a fresh source. History counts and global journal search no longer include deleted entries.

The information view uses the native [HTML auto popover](https://html.spec.whatwg.org/multipage/popover.html#the-popover-attribute), supported within the project's Chrome 116 minimum. It closes via its close button, Escape or native outside dismissal. Escape closes information before clearing a journal search. Reading information sends no worker mutation. Filtering, account changes or record replacement close information that is no longer in the displayed list.

The existing worker-only current-episode snapshot now includes a small ephemeral playback summary. The tracker reports earned confirmation seconds and playing/paused/buffering/seeking state; polling neither advances the timer nor writes it to the journal. The worker validates the account, episode key, state and integer range 0–30 and forwards only seconds/state. The panel displays **Подтверждение позиции: 12 из 30 секунд** without interpolating time. Unavailable/stale media, changed source/episode, stopped tracking and disabled/account-changed configuration do not reuse a previous countdown. Confirmed progress remains separately durable.

Journal rows retain their DOM identity and icon controls while their values update. Open information follows the same record without replacing its focused close control. Focus is preserved through updates and reordering; when the focused row or information leaves the selected list, focus returns to that list's filter (or the results heading during search). Important result transitions are announced independently of per-second confirmation updates. Threshold-only changes update the list immediately; paused tracking no longer promises automatic completion. A resumed unsent episode also clears the tracker's local finished marker without reloading the page.

## User flow

Open the real Chrome side panel, select **MyShows**, then **Подключить MyShows**. The extension opens the MyShows history page, reads its existing token through an isolated content script, validates it at `/scrobble/check`, and binds the connection to the signed-in profile. It never creates or rotates a token automatically. Missing login/token/scrobbling access is reported with a recovery action. Successful connection enables future tracking; previous viewing history is not imported.

Actual played ranges are sampled once per second and saved roughly every ten seconds, on pause and when the page is hidden. A union of ranges avoids counting rewatches twice. Seek jumps, pauses, media/episode transitions and sampling gaps over 15 seconds do not count as played coverage. From 0.6.4, a separate confirmed player position can increase effective progress as described below. Different-duration cuts reset incompatible coverage and position credit. Account, Rezka title ID, season and episode identify a local record across tabs and supported mirrors. The default threshold is 90%; a slider allows any whole percentage from 1% to 100%, displaying changes immediately and saving on release or a keyboard step. Already queued/completed/cancelled entries are not submitted again.

### Progress after seeking (0.6.4)

After seeking or starting at a saved position, 30 seconds of actual playback confirms the current position. Confirmation time is limited by both elapsed wall time and media advancement divided by playback rate, so 2x playback does not turn the wait into 15 seconds. Pauses and buffering preserve the earned seconds but add none. Further seeks in either direction, changed media/episode identity, disabled tracking, a changed account, or an observation gap over 15 seconds restart the confirmation window. Replacing a video source also restarts confirmation.

The tracker attempts a save immediately when the window first completes; subsequent positions use the normal save cadence. `confirmedPosition` stores the furthest confirmed media time independently of actual `ranges` and `watchedProgress`. Effective `progress` is the greater of unique played coverage and confirmed position divided by duration. Rewinding cannot reduce it or fabricate played ranges. The existing threshold, queue, exact-match checks and duplicate protection remain in use. A seek to the end followed by less than 30 seconds of playback contributes only actual coverage.

Failed saves retain both measured ranges and confirmed position. Confirmed progress survives browser/worker restarts; an unfinished confirmation window is local to the page and starts again after reload. Existing unfinished records catch up after 30 seconds of new playback at the resumed position; no historical positions are guessed or imported. The panel says **Учтено** and identifies position-based progress rather than presenting skipped footage as measured playback.

The media-state behavior follows the [HTML Standard's seeking algorithm](https://html.spec.whatwg.org/multipage/media.html#seeking) and [playback model](https://html.spec.whatwg.org/multipage/media.html#playing-the-media-resource). The extension observes native media state and events; no new player API or permissions are required.

The panel exposes **Очередь**, **Внимание**, and **История**. Each entry includes season/episode, status, explanation, and an expandable transition history. Search spans all three lists for the connected account, temporarily hides the list filters, and restores the selected filter when cleared. Long lists show 50 records at a time. Retry checks a previously submitted record before doing anything else. Cancellation disables further work for that episode without unmarking MyShows. Turning off automatic marks pauses collection and processing; disconnect also removes the saved token. Journal records remain associated with their original account. In-flight requests may complete after pausing.

### Manual episode marks (0.6.1)

**Текущая серия → Засчитать серию** reads the selected episode from the active Rezka top frame, including before playback begins. The panel refreshes the snapshot once a second while open, with at most one read in flight. On submission the worker obtains it again and requires the displayed episode key, active tab, matching loaded build, source URL/title ID and connected account. A stale episode/tab is rejected rather than silently marking the new selection. Unfinished or cancelled entries that have not been submitted also expose **Засчитать серию** directly in their list.

A manual request bypasses only the playback threshold. It sends 100% to MyShows without fabricating local played ranges or overwriting measured progress. `manualAt` and the transition history record the explicit request. `manualPending` allows that one entry to run while automatic marks are off, without enabling or processing the rest of the queue. The request remains durable after a worker/browser restart. Turning automatic marks off explicitly also pauses pending manual work; account mismatch clears manual work permissions. Retry can resume a failed manual request. Repeated clicks and previously submitted uncertain records never issue another POST. Automatic exact-match, signed-in account and final watched-state checks remain mandatory.

### Cancellation and resumed tracking (0.6.2)

The current episode and journal rows expose **Отменить отправку** before submission, or **Остановить синхронизацию** after submission, including while sending/confirming/checking. Cancellation saves a terminal state, clears manual work permission, and closes only that job's owned MyShows tab. Late replies can retain accepted-match metadata but cannot revive the job or begin another confirmation. A native request already issued may still finish remotely; cancellation does not undo a watched mark on MyShows.

Cancelled episodes appear as **Отменено** in the current-episode section and history, with an explicit count and explanation. **Продолжить отслеживание** is available only when no submission is outstanding. It clears the manual request and preserves measured ranges/progress, returning the episode to ordinary threshold-based tracking without turning automatic marks on. Uncertain submitted records instead link to MyShows for inspection and cannot be reset into a duplicate POST. Existing history and cancellation events are retained.

### Local reset after a remote change (0.7.2)

Completed movies and episodes expose **Сбросить запись** in both the current-view block and their journal row. Use it after removing a watched mark directly on MyShows. This is a local action: it does not remove or add a watched mark, rating or scrobble on MyShows. It is also available while disconnected, for the journal's selected account.

Reset clears the local success and all credited progress, submission/match metadata and manual-request flags. It creates a fresh record ID and source for the same account/media key while retaining the bounded event history, including the explicit reset event. The record stays in **История** as **Сброшено в расширении**. **Засчитать фильм / Засчитать серию** becomes available in both views; it creates a new manual submission using the normal exact-match, confirmation and watched-state verification flow. Automatic marks can remain paused.

Reset is deliberately terminal for automatic tracking: old player batches, a threshold change, alarms or a browser restart cannot recreate the removed mark. The next mark requires an explicit **Засчитать** action. Double reset requests and stale actions against the old ID are rejected. Only completed records can be reset; uncertain/in-flight submissions retain their reconciliation path and duplicate protection. A reset never clears another account or another episode. The journal remains a history of synchronization, not a continuous mirror of changes made on MyShows.

### Resume tracking after journal removal (0.10.1)

Removing an unsent cancelled entry leaves an account/media-key suppression so delayed player batches cannot recreate it. The current film or episode then exposes **Возобновить учёт** alongside manual completion. Restoration re-reads the active Rezka top frame and validates its build, media key and connected account before atomically replacing that suppression with a fresh `watching` record. Repeated or stale requests fail without changing another record. Global automatic-tracking settings remain unchanged; a paused account gets an instruction to enable automatic marks.

The new record starts with zero credited progress, no played ranges and a new source identity. Restoration itself neither submits a request nor marks anything in MyShows. Ordinary played coverage and the existing 30-second position confirmation apply to subsequent playback. The page resumes sampling without a reload. A persistent `trackingEpoch` binds subsequent batches to this viewing: previously buffered progress, late stop replies and failed saves from before restoration cannot credit or stop the new viewing, including across open tabs and worker restarts. Restoration is explicit; playback, threshold changes and restarts do not silently undo journal removal.

## Matching without IMDb (0.12.2)

The worker previously rejected any unsent entry without IMDb before calling MyShows, even when Rezka provided the title, release year and episode selection. This also made **Повторить** return the same error indefinitely on titles with no IMDb listing.

The [official identifier guide](https://myshowsme.github.io/myshows-scrobbler-api/en/scrobbling/ids) permits title and year when IDs are unavailable. The [reference converter](https://github.com/myshowsme/myshows-scrobbler/blob/main/src/scrobblers/converter.ts) retains an empty `ids` object and omits empty individual IDs. The extension follows this shape for films and shows, keeping season/number for episodes. Without IMDb or a release year it still stops with an explanation of the missing data.

Title/year submissions never authorize automatic native confirmation, including when the API returns `match=exact`. A guessed object ID is not pinned: the user can correct the match and confirm it in MyShows history. **Проверить** then reconciles the same source and verifies the final watched state without another POST. Existing missing-IMDb entries can use **Повторить** after the update; there is no automatic migration that sends old attention/cancelled entries or changes the global pause.

Offline regression checks cover the tracker-to-worker path without IMDb or an original title, films and episodes, recovery from saved identity errors, missing-year rejection, correction of a guessed match, restart and duplicate prevention. The user's existing Chrome page confirmed the missing IMDb link before the fix. Live acceptance of the fallback payload and the updated toolbar panel still require the installed-extension acceptance sequence in [development.md](development.md).

## Worker and remote effects

The MV3 service worker owns all state writes and serializes them. A one-minute alarm is recreated on startup. Work is single-flight, bounded to eight entries per run, with exponential backoff (up to one hour) and at most five automatic attempts. Missing login or a different browser account pauses the integration. Invalid tokens disable it until reconnection. Queue and history use `chrome.storage.local` under `myshows:state`.

Before an outgoing write, the worker checks the browser account and persists submission intent. It sends one `/scrobble/stop` request after the local threshold. Each entry has a unique 28-character `source_app` value (`Rezka-` plus the full UUID encoded as unpadded base64url), allowing reconciliation with exactly its own history card. The 51-character format from 0.6.0/0.6.1 was rejected by the live API; the compact format was accepted. Only a response with `action=scrobble`, `match=exact`, the expected `objectType` (`episode` or `movie`), and a valid object ID permits automatic native confirmation. IMDb identity from the Rezka page, plus season/episode for episodic content, is required for automatic confirmation; titles alone never authorize an automatic mark. Submissions without IMDb follow the manual matching path above.

Confirmation runs in a temporary inactive MyShows tab using the site's existing **Подтвердить** button. It checks account, unique source, media type, matched object ID, pending status and threshold before clicking (plus season/episode for episodic content). It then loads the film or episode page and requires the watched movie status described above or the checked `EpisodeDetails__watch-label` before reporting **Отмечено**. Only tabs created by this module are closed. A failed connection tab remains available for sign-in/token setup.

The worker checks the expected origin/path and waits for the content script's reply rather than requiring the entire tab to finish loading. Unrelated advertising resources can keep a usable MyShows document in the `loading` state. A reply from the wrong document is retried within the bounded wait.

A lost reply, interrupted worker, HTTP 5xx, or unreadable successful response never triggers an automatic duplicate POST. The worker searches history by its persisted source. If exact-match evidence was lost, pending records require native user mapping/confirmation; already-approved records can be verified. HTTP 401/403/429 are treated as rejected requests, with credential recovery or delayed retry. Uncertain, missing, changed-layout and matching failures stay visible, rather than becoming successful history entries.

Explicit HTTP 400/404/405/410/413/415/422 rejection clears submission intent and exposes a retryable attention state, without searching history for a record that was not accepted. Recognized validation failures get a specific explanation; only sanitized error metadata is saved. Startup repairs legacy entries only when their journal explicitly records rejection and contains no accepted-match/confirmation evidence. Cancelled entries remain cancelled, and uncertain writes retain their original source and reconciliation-only behavior. Unsent entries use the compact source on their next submission.

## Boundaries and limitations

- The MyShows site must stay signed in in the same Chrome profile. Scrobbling is advertised as a MyShows PRO feature. The API and native UI may change independently.
- Tokens are stored only in extension-origin IndexedDB, not `chrome.storage.local`, logs, source files, panel state, page globals or URL parameters. This is local browser storage, not an encrypted credential vault. Only the fixed MyShows API endpoints receive the Bearer token, with redirects rejected. The native confirmation uses existing site authentication without extracting its cookies.
- Rezka content scripts may report validated top-frame playback only. Panel controls and site commands have separate sender checks. Arbitrary page-world messages cannot obtain the token or call the confirmation adapter.
- The native HTML5 video must be present in the top document, alongside either active Rezka episode controls or a matching native movie initializer. Cross-origin iframe-only players and ambiguous episode numbering require attention or are not tracked. Missing IMDb identifiers use title/year submissions requiring manual native confirmation; missing both IMDb and year prevents submission. No guessed title-only matches are automatically confirmed.
- Very short sessions and abrupt process termination can lose the final unsaved sampling interval (normally up to ten seconds). A suspended background tab can undercount long sampling gaps and reset an unfinished position confirmation. Position credit represents the user's accepted seek/resume behavior; it is kept separate from measured played coverage.
- Duplicate prevention is local to this extension installation/profile. Other clients and manually added MyShows marks are not imported. The saved journal records past synchronization results, not a live mirror of later manual changes on MyShows.
- Journal storage is local and remains until extension data is removed. It contains title metadata, played ranges and synchronization outcomes; no export, cloud backup or automatic history deletion is implemented. Each entry retains its latest 30 transitions.
